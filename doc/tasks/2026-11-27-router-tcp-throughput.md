### 2026-11-28　首次窗口预算（插件 100 Mbps）

RTT 是数据发出到确认返回的往返时间。每个活跃方向的目标在途量按带宽时延积计算，字节数等于 bit/s × RTT 秒 ÷ 8。

| 平台 | 设计带宽 | 设计 RTT | 单方向有效数据目标 | 建连后自适应起点 |
| --- | ---: | ---: | ---: | ---: |
| AX56U V2 路由插件 | 100 Mbps | 300 ms | 3,750,000 B（3.58 MiB） | 256 KiB |
| Probe Node、Android | 500 Mbps | 300 ms | 18,750,000 B（17.88 MiB） | 256 KiB |

- TCP 读写分别计量，按约 300 ms 的采样周期折算流量。单方向达到当前预算的 1/4 时，下一预算取当前的两倍和本期需求的四倍中较大者，并限制在表中目标。突发足够大时一次采样即可到顶。
- 持续用量最多为预算的 1/8 时，每满 30 秒将该方向预算减半。用量回升超过低水位即取消本轮倒计时。从满额持续空闲到起点，路由器约需 2 分钟，Probe 和 Android 约需 3 分 30 秒。关闭连接即移除采样状态，已排队数据由 TCP 按确认和消费进度释放。
- 表中数字是有效数据预算。Linux 的 socket 缓冲和 gVisor 的内部缓冲另计报文开销。握手前协商缩放，建连后按需调整，窗口上限不等于实际分配内存。缩小预算只影响后续入队，正常 ACK、拥塞窗口和对端通告窗口仍约束实际发送速度。
- 内层覆盖插件自己终止的 TCP（含 SNI 代理两端及经出口的外部下载测速）、Probe 出口 gVisor、Android VPN gVisor。透传的 LAN 原始 IP 包保留终端自己的 TCP 窗口。外层 WebSocket/TCP 的新拨号及服务端监听按对应平台准备窗口；权限受限的 Android/Linux 原生 socket 保留系统自动调节，设备内核可能限制上限。
- 原始 UDP 无 TCP 窗口。Probe 和 Android 的 H3/QUIC 接收流控由 QUIC 自动增长，单流初始 512 KiB、上限 18,750,000 B，单连接初始 1 MiB、上限 37,500,000 B。对端已经收到的 QUIC 流控额度持续有效。
- 51.1 的 Linux 4.1.52 在握手时使用系统接收上限协商缩放。现场只读值为 tcp_rmem 最大 1,980,096 B、rmem_max 为 524,288 B。单独设置 socket 缓冲后，实机回环的两端缩放仍为 5（可表示 2,097,120 B）。插件启动时若两项上限均不足，则把系统 rmem_max 提至 3,750,000 B，保留默认缓冲和 tcp_rmem；原值保存在 /var/run，正常退出或崩溃后清理时，在当前值仍由插件持有的情况下恢复。写入受限时使用系统现值。内核依据见 [Linux 4.1 tcp_select_initial_window](https://github.com/torvalds/linux/blob/v4.1/net/ipv4/tcp_output.c#L223-L232)。
- 现场拥塞控制快照：AWS SG 默认 cubic，抽查 8 条 TCP 12040 连接均为 cubic；51.1 的默认算法也是 cubic，两端当时均未启用 BBR。此次窗口策略独立于拥塞算法。
- 验证：Go 和 C 覆盖突发增长、连续低负载减半、突发打断回落及下限；Go 还检查方向计数、连接关闭注销及 gVisor 预算。Linux 回环在允许目标窗口时双端缩放为 6，建连后接收缓冲记账值从 7,500,000 B 降至 524,288 B。隔离的系统参数测试覆盖停用恢复及保留管理员修改。上述带宽为设计目标，51.1 到 AWS SG 的实际吞吐待新版本现场测试。

### 2026-11-28　缩短路由器内层 ACK 的转发等待

- 基线为 51.1（节点 26）经 AWS SG（节点 27），两端均为 v0.4.142。节点间下载两次为 96.1、96.8 Mbps，10 秒外部下载样本为 9.4～14.7 Mbps。独立采样匹配到 4,535 个纯 ACK，从 TUN 出现到 WAN 发出的延迟中位数为 24.0 ms，P95 为 114.9 ms。
- 每轮 poll 返回后，插件先摘除出错的承载槽位，再读取就绪的 TUN 包。所有承载先处理待写数据，随后分别处理可读数据。TUN 新产生的帧可以在本轮尝试一次非阻塞写；遇到 TLS 背压后按 OpenSSL 要求等待读或写就绪，并保持原帧顺序。
- 每条可读承载每轮最多处理 16 次 TLS 读取，每次处理完后检查 2 ms 时间预算，达到预算就让出。已解密的数据可触发下一轮立即处理。TUN 的 16 包／4 ms 预算和每条承载的写预算沿用原值。
- 回归场景覆盖两个槽位同时有工作、TUN 新帧当轮写出、写阻塞时读方向继续推进及按序重试。现场验收使用同一路径分别记录节点间和代理下载速率，并比较 TUN → WAN 的纯 ACK P50、P95。

### 2026-11-28　200 Mbps、300 ms 验收口径

- 插件单流目标为 200 Mbps、端到端 RTT 300 ms。每个活跃方向至少需要 7,500,000 B 有效在途数据，窗口预算上限取 10,000,000 B。连接从 256 KiB 自适应增长，低负载每 30 秒减半，从上限回落到起点约需 3 分钟。按需设置 51.1 的握手接收窗口上限，退出时恢复。Probe 出口和承载有 18,750,000 B 的有效数据预算。
- 外部测速可选同一 Cloudflare 测速源的 HTTP 或 HTTPS。两种协议均为单连接、最多 10 秒或 64 MiB。HTTP 用 TCP 80，便于测量透明转发。HTTPS 用 TCP 443。节点模式仍走经认证的外层 TLS，两个模式按各自的 TCP 源和目标端口匹配测速流量。
- 分别记录 300 ms 隔离网络的窗口验证和实际路由器到出口的吞吐。以稳定期吞吐、TCP 重传超时、TUN 水位与丢包判断现场容量。
- 本地 Linux 用独立 veth 两端各注入 150 ms 延迟，以纯 HTTP 传输 320 MiB。发送端 TCP_INFO 的数据阶段 RTT 约 300 ms。旧 3.75 MB 窗口测得稳态 107.52 Mbps。新窗口协商缩放为 8，稳态 229.88 Mbps，含窗口增长阶段的全程均速为 199.70 Mbps。

### 2026-11-28　Probe Node 与 Android 的总预算

- 500 Mbps 是节点总设计带宽。按 300 ms RTT 计算，每层的有效在途数据预算为 18,750,000 B。内层 gVisor 的所有连接和两个方向共享一份预算。可调节的外层 TLS/TCP 套接字也按同样规则共享一份预算，承载层的重复缓冲单独记账。
- 有竞争时，空闲方向保留小窗口，活跃方向按请求量分配剩余窗口。更新时先缩小需要让出的窗口，再扩大获得份额的窗口。关闭连接后，它的份额可在下一次采样重新分配。
- Probe 的出口转发与本地路由代理不再为每条目标站 TCP 连接固定申请 4 MiB 收发缓冲。可调节的目标站 TCP 套接字共享一份外部连接预算，Android 的 VPN 直连也使用这套分配。无调窗权限时保留操作系统的默认调节。
- Probe 出口下行流量共用一个 500 Mbps 调速器，整台节点只保留一个 64 KiB 的突发额度。每条流仍按下游队列和写阻塞独立减速。窗口是可在途的数据预算，实际常驻内存还包括报文开销、尚未释放的排队数据和其他进程状态。
- Probe 的 H3/QUIC 兼容承载共享 18,750,000 B 接收额度。流初始接收额度为 128 KiB，连接初始接收额度为 256 KiB。已有连接的通告额度只在连接结束后回收。初始额度不足时拒绝新的 H3 连接，现有连接可继续使用已通告额度。
- AX56U V2 插件按 200 Mbps、300 ms 的目标设计，保留 10,000,000 B 的每层窗口预算。所有 TLS 承载槽位共享外层预算，SNI 代理的套接字与经节点测速套接字共享内层预算。窗口分配按两种方向的实际读写需求调节。
