## 一、需求定义

### 1.1 背景与问题

用户希望在 ASUS RT-AX56U V2 上运行现有 CloudHelper fake IP 路由能力，并作为其他 Probe 可连接的物理链路节点。当前原厂固件已经通过 SSH 只读检查，但现有发布未提供 ARMv7 程序，尚未验证模块加载、程序运行、启动持久化或业务流量。

### 1.2 目标

交付专供路由器、以新代码结构实现、可安装在当前华硕原厂固件上的独立插件发布产物，以同一节点身份提供DNS分流、fake IP代理和双角色12040物理链路；保持现有主控与Probe协议兼容，12040服务端明确绑定WAN口IP。

### 1.3 范围、非范围与约束

- 范围内：ARMv7 插件运行时；DNS 与 dnsmasq 集成；fake IP 数据入口及转发；12040 监听、主动连接、认证、断线重连；必要的主控身份/配置兼容；安装、启停、卸载及可持续升级适配。
- 管理范围：插件提供轻量小Web控制台和受认证管理API；华硕后台增加单独的“CloudHelper”菜单入口是目标集成项，必须验证当前原厂固件兼容、重启恢复及卸载。管理Web默认只绑定LAN管理地址，端口待实机冲突检查确定；12040仅为WAN物理链路，不混用管理端口。
- 小Web最小能力：总开关/状态、节点身份和主控连接设置（机密不回显）、DNS上游与启停、规则/映射查询、12040服务端/客户端与对端状态、限量日志和诊断、安装版本/更新状态。业务规则与映射沿用主控权威来源，本地页面不得创造另一套冲突规则。停止服务须保留可恢复的管理入口或明确管理脚本恢复方法。
- 独立代码与产物：规划仓库新增 `router_plugin/`，独立Go module、命令入口、路由器运行时和测试；独立资产、安装/服务标识、清单与升级选择。既有Probe代码作为协议/行为参考，不把它裁剪、换tag或改名作为新实现。发布版本策略需设计，不推定必须拆仓库。
- 路由器特点：控制缓存、并发、队列及日志的上限；减少Flash写入并合并必要持久化；优先小依赖集合；配置与映射采用一致快照；WAN/DNS/防火墙恢复幂等；生命周期可回滚。暂不以零依赖或绝对吞吐作未经验证的承诺。
- 12040 服务端只绑定当前选定活动 WAN 的实际 IPv4 地址，不能回退到 `0.0.0.0` 或 LAN 地址；适用配置启用的 TCP 和 UDP 监听。WAN 未就绪时明确报告并等待，地址变化后关闭旧监听、认证配置保持一致并绑定新地址。客户端须经物理 WAN 出站且避免 TUN 回路；具体出口约束按现有拨号适配。
- 第一目标设备：SSH 别名 `localrouter`，地址 `192.168.52.1:22`；RT-AX56U V2；原厂 `3.0.0.4.386_52332-gfbf3b9c`。
- 范围外：刷 Merlin/OpenWrt 或重编整套固件；替代原厂 Wi-Fi、AiMesh、DHCP、NAT；完整软路由产品及 Mihomo 订阅/出口管理；与本目标无关的控制器功能。
- 初始数据入口采用 TUN，属于当前代码和实机能力支持的设计方案，用户尚未明确指定入口；如后续改用 TPROXY，更新本账本与决策。
- 默认仅接管 fake IP 网段，避免自动创建全局接管路由；普通流量使用原厂转发。虚拟节点地址等协议必需路由在设计中单独列明。
- DNS初始参考现有语义：代理规则A查询返回fake IP，直连返回真实IP，拒绝返回REFUSED；这是行为兼容方案，并非用户要求所有域名都返回fake IP。
- 继续使用控制器权威 fake IP 分配与身份/路由授权；不得在插件内自行分配与全网不一致的映射。
- 12040“服务端”指接受其他 Probe 的物理 Carrier 连接；是否还承担其他节点的互联网出口功能需单独设计，不把监听成功当成出口验收。
- 既有生产 Probe/Controller 二进制沿用在线更新交付；SSH 用于诊断和验证。首装插件方式需在安装设计中明确，不把只读连接授权解释成手工替换生产程序授权。
- 不使用 HomePc 做构建或测试；必要的 Linux 隔离验证使用本地 WSL。
- 工作区已有备用出口任务的未提交改动，不回退、不混入提交、不据此声称插件功能已实现。

## 二、总体架构

### 2.1 当前现状

- DNS：`probe_virtual_router_dns_service.go` 在 `198.18.0.2:53` 监听 TCP/UDP；代理规则 A 查询请求主控映射；非 A 查询走真实上游。目前 AAAA 可能导致 IPv6 绕过。
- DNS 上游与缓存：`probe_virtual_router_dns_cache.go`；Linux 系统 DNS 适配：`probe_virtual_router_dns_system_linux.go`，默认处理 resolv.conf/systemd-resolved，不能未经适配直接套用到华硕。
- IP 包入口：`local_tun_install_linux.go`、`probe_virtual_router_tun_dataplane_linux.go`、`probe_virtual_router_linux.go`；`probe_virtual_router.go` 按映射/路径封装并转发原始 IP 包。
- Carrier参考实现：`probe_virtual_router_runtime.go`；默认12040，已有TCP/TLS WebSocket、UDP/HTTP3监听、客户端worker与重连。新实现必须按所支持的既有传输配置互通，逐项验证，不创造不兼容端口协议，也不默认承诺全部旧功能已搬入。
- 产品：普通 Probe 默认可能修改系统 DNS和全局路由；`linux_router` 限制 amd64/arm64 并带有原厂路由器不需要的完整软路由/Mihomo功能；两者均不等于现成华硕插件。
- 原厂 dnsmasq 使用 `bind-dynamic`、`no-resolv` 和 `servers-file=/tmp/resolv.dnsmasq`，监听 LAN/本机 53 并承担 DHCP。

### 2.2 目标架构

在 `router_plugin/` 建立新的路由器专用实现，独立 `go.mod` 和 `cmd/cloudhelper-router-plugin/` 入口。暂定内部单元为 `internal/dns`、`internal/policy`、`internal/controller`、`internal/dataplane`、`internal/carrier`、`internal/platform/asuswrt`、`internal/lifecycle`、`internal/status`、`internal/web`；静态页面在 `web/`，路径在实现前可细化。

现有Probe源码仅为协议、映射、认证及路由行为的参考，协议契约通过跨实现测试固化。第一目标华硕ARMv7；平台接口为其他路由器保留适配边界，不把OpenWrt已支持或通用路由器兼容作为本次已完成成果。

新数据面首选TUN接收原始IP包并封装到兼容Carrier，在入口侧避免仅为转发加载完整用户态TCP/IP栈。是否需要本机承担其他节点的最终互联网出口，及相应协议栈依赖，须在设计中明确；12040服务端接入并不自动等于出口角色。QUIC、认证与DNS等依赖按必要契约逐项选择，ARMv7和旧内核支持用实际构建及运行证据证明。

小Web由插件管理单元提供LAN专用监听，使用小型静态HTML/CSS/JS，按需轮询有界状态，不引入重型前端服务。菜单集成与业务运行分离：只读查到原厂 `state.js` 通过RequireJS加载 `require/modules/menuTree.js`，点击逻辑使用 `location.href`。当前 `/www` 在只读SquashFS中、无user*.asp页面、无overlayfs；可研究在可写目录生成菜单文件并做可撤销的运行时文件绑定挂载，但尚未操作或证明成功，且必须保留ASP模板指令、处理菜单缓存和固件版本差异。不能以找到文件即宣称已支持菜单插件。

```text
LAN 客户端 DNS -> 原厂 dnsmasq -> 插件 DNS -> 规则 + 主控 fake IP 映射
                    |              |
                    |              +-> 真实上游 DNS（不得回指 dnsmasq）
                    +-> DHCP/局域网名称解析

LAN fake IP 数据 -> Linux 路由/转发 -> TUN -> 插件虚拟路由
                                               |
                                               +-> 12040 客户端 Carrier -> 其他节点/出口
其他 Probe -> WAN IPv4:12040 服务端 -> 认证后的 Carrier -> 既有虚拟路由处理
回包沿对应链路 -> TUN -> LAN 客户端
```
